## 💡 오늘의 핵심 인사이트
- 문자열 전처리에서 **정규식 `re.sub(r'[^a-z ]', ' ', text)`** 를 사용하면 구두점 제거와 공백 치환을 한 번에 처리할 수 있다.
- **금지어 목록(banned)은 `set`으로 변환**해야 조회 시간이 O(B) → O(1)로 최적화된다. `in` 연산은 list에서 O(N), set/dict에서 O(1).
- `dict.get(key, 기본값)` 패턴은 카운트 초기화 분기(`if key in dict`)를 제거해주는 파이썬다운 문법.
- `max(word_count, key=word_count.get)`은 **딕셔너리의 value 기준으로 최대 key를 찾는** 관용 표현. 정렬 없이 O(N)에 해결 가능.
- 같은 로직을 `collections.Counter`로 쓰면 더 간결해진다. (다음 리팩토링 목표)

## 📊 복잡도

paragraph의 길이를 P, banned의 원소 수를 B라 하자.

- **시간복잡도 O(P + B)** :
  - `lower()` + `re.sub()` + `split()` : 각 O(P)
  - `set(banned)` : O(B)
  - 단어별 금지어 체크 + 카운트 : O(P) (set 조회 O(1) × 단어 수)
  - `max(...)` : O(W), 서로 다른 단어 수 W ≤ P
- **공간복잡도 O(P + B)** : 
  - cleaned 문자열 O(P), banned_set O(B), word_count 딕셔너리 O(W)

## 📌 재발 방지
- `in 리스트` 대신 **`in set`** 을 습관화하기. 특히 반복문 안에서 조회할 때 성능 차이가 극명함.
- 정규식 `[^a-z ]`에서 **공백을 패턴에 포함**시켜야 단어 경계가 유지됨. 빼먹으면 단어가 붙어버려 버그 발생.
- 카운트 문제는 기본적으로 **`collections.Counter`** 를 먼저 고려하기.
- 다음번에는 **Counter 버전으로 리팩토링**해서 두 풀이를 비교 정리하기.
- 문제 분류(Hash Table)를 보고 **해시맵 기반 카운팅** 접근을 떠올리는 훈련하기.
